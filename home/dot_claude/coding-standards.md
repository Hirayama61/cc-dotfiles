# コーディング規約

## 読み手の想定

想定読者は、新規でこのプロジェクトに参画した人。（もちろん書いた本人も含むが、人間は数日で自分が書いたコードを忘れる）
「今の文脈を知っていれば分かる」は、満たしていないものとして扱う。

実装前に同種のファイルを複数調べ、主流のパターンを把握してから書く。
ただし「既存に N 箇所ある」は読みやすさの根拠にならない。
一貫性は探すコストを下げ、可読性は読むコストを下げる。
それらは異なる軸のコストなので、前例が多いことは読みやすさを保証しない。

## 命名

- 関数名は、本体を読まずに「何を受け取り、何を返し、何を変えるか」が言えること。
  名前に表れていない副作用や処理があるなら、名前を直すか関数を分ける。どちらかは必ず直す。
- 中身のない語だけで名前を作らない。
  `data` `info` `item` `value` `manager` `handler` `processor` `util` `helper` `temp` `result`。
  修飾語を足して具体的にするか、扱っている対象そのものの名前を使う。
- 名前の長さはスコープの広さに合わせる。
  数行で閉じるループ変数は短くてよいが、ファイルをまたいで使うものは省略しない。
- 真偽値は `is` / `has` / `can` / `should` で始める。
  名前自体を否定形にしない(`!isNotReady` のような二重否定を生む)。
- 単位や形式を読み違えやすい値は、名前に入れる(`timeoutMs` / `sizeBytes` / `rawHtml`)。

## 塊と空行

- 空行は段落の区切り。空行で挟まれた塊は 1 つの意図だけを持ち、
  「この塊が何をしているか」を 1 文で言えること。
- 意図が変わる位置で空行を入れる(前提の検査 → 組み立て → 返す、のような切れ目)。
- 1〜2 行ごとに空行を入れて全体を分断しない。塊が消え、段落として読めなくなる。
- 空行の代わりにコメントで塊を説明しない。
  塊が読めないのは名前か分け方の問題であって、コメントで補う問題ではない。
- 関数を 1 文で説明できないなら分割を検討する。
  説明に「〜して、そのあと〜する」と接続詞が要るのが目印。

## 流れ

- 前提の検査は早期リターンで先に片づけ、本筋をネストの浅い位置に置く。
  検査の早期リターンは拒否かエラーを返す。素通しにしてよいのは、それが安全側だと言える時だけ。
- 変数は使う直前で宣言する。宣言と使用箇所を離さない。
- 複雑な条件式には名前を付け、説明変数として切り出す。

## コメント方針

- **既定はコメントなし**。コードと命名で意図を表現する。
  書く前に「これはコードから読み取れないか」を自問する。
- **書くなら「なぜ要るか」を書く**。何をしているかはコードが言う。
  「だから何?」と返せるうちは実装の言い換え。
  例: 「空文字を除外する」ではなく
  「取込 API が退会済みを空文字で返すため、除かないと一覧に空行が出る」。
- 書いてよいのは次の4つ。ここに無いものは書かない。

  | 種類 | 中身 |
  |---|---|
  | ファイル冒頭のヘッダ | そのファイルの役割・責務・判定順序 |
  | 前提・制約 | 外部仕様、順序依存、既知の落とし穴。検査や防御が要る理由もここ |
  | workaround | 何が原因で、どうなれば外せるか |
  | TODO | 未着手の作業 |

- **短く書く**。1 コメントは 3 行が目安。
  超えるときは本質が絞れているか疑う。
  長くなるときは一文を短く切り、文が終わったら改行する。1 行に詰め込まない。
- **時間経過で陳腐化するフロー情報を書かない**。
  「現在は」「新しい」「以前は」「一時的に」のような相対的な時制、変更したという事実、
  他ファイルの行番号。いずれも読まれる頃には合わなくなる。
- **経緯・採否理由・レビューア向けの正当化を書かない**。
  なぜ今その処理が要るかは書くが、どういう議論を経てそうなったかは書かない。
  読み手は変更を見ていない。経緯は Decisions ノート(外部脳)・コミットメッセージ・PR 説明に置く。
- **番号は TODO にだけ書く**。issue/PR 番号を貼っても、読み手は説明になっていない
  PR に飛ばされて情報を探す羽目になる。コードはそれ自体で完結させる。
- **消してよいのは、それが説明していた処理を消すとき**。
  上の4つに当てはまらないコメント(言い換え・経緯)は、触った箇所なら削ってよい。
  周辺がコメント過多でも倣わない。
